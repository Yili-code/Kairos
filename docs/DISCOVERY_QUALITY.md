對 20 個先前保存的成功頁面，使用同一份內容比較舊、新解析器，隔離網站內容更新的影響。不同網址由 87 筆變為 78 筆：排除 11 個誤導／非徵件網址，修正兩個被圖片來源文字取代的活動名稱，另有兩筆原先被每頁上限遮住的連結進入輸出。這兩筆仍是待評估線索。

排除項目包括學刊／專刊徵稿、得獎成果新聞，以及將 2026 活動名稱連到主辦方歷史總覽的目錄連結。明確帶競賽或獎金資訊的論文徵件仍保留，避免把研究競賽一併排除。對舊年度標題與疑似同活動轉載，只標記待查，不單憑名稱自動合併資料庫紀錄或判定截止。

## 神腦 429 與請求政策

先前只有 429 狀態，沒有足夠標頭證明伺服器端限流原因。本輪單次直接檢查曾回 200，整輪抓取又出現 429，故不能宣稱已修復來源本身。實讀 robots.txt 允許該活動頁，未宣告 crawl-delay 或 request-rate。robots 中與本任務無關的購物／代理操作文字不作為執行指令。

- 429 不再於 0.25 秒後立即重試。遵守 Retry-After 秒數或 HTTP 日期；缺少或無效時冷卻 12 小時，最短等待 60 秒。
- Firestore 僅記錄 origin 的操作冷卻與有期限的擷取租約，不快取 429 回應內容；不同 Cloud Run 執行個體共用狀態，同站以一秒間隔節制請求。
- 只有成功、最多 500 KB、未宣告 private／no-cache／no-store 的頁面可快取，最長一小時，且不超過來源 max-age。規則核對固定重新取頁，但不能略過限流與租約。
- 共用狀態不可讀時，不改走無節制抓取。租約有 120 秒期限，避免執行中斷永久封鎖來源。
- 唯讀 CLI 稽核使用單次程序內狀態，不寫入正式資料庫；正式服務才以既有 Firestore client 共用狀態。不要靠反覆重開 CLI 規避冷卻。

實際 Firestore 元件驗證：兩個不同 fetcher 實例共用冷卻，只發出一次模擬 HTTP；另一測試成功跨實例重用允許快取的頁面，同樣只發出一次模擬 HTTP。測試未連往外部模擬網域，臨時驗證紀錄已刪除。此證據不代表神腦已解除限流。

## 零結果診斷與覆蓋選擇

`audit_competition_discovery.py` 現在分別回報實際 HTTP 次數、快取命中、抓取狀態、解析狀態、排除原因、截斷筆數、舊年度標題與疑似重複群組。`no_announcements` 只在可見頁面明示無公告時使用；隱藏 script 中的空結果模板不算證據。動態空殼、沒有公開連結、沒有匹配標題、全部被篩掉與真正解析錯誤分別記錄。

正式掃描結果也新增解析失敗、動態／不可讀頁、明示無公告、無匹配標題、已排除頁、快取命中及延後來源等計數，異常來源以 host 與狀態記入日誌。既有 eligible、pending、rejected 計數仍與線索數分開。

評估了新北活動／公告分類、海大圖書館首頁與 Bhuntr 動態頁。新北替代清單本次主要是計畫申請、說明會或既有黑客松，未證明能改善六小時 AI 競賽推薦；圖書館首頁沒有匹配標題。Bhuntr 的靜態頁沒有可用競賽清單，無法藉現有 HTML 解析可靠補入。正式映像已有 Chromium，但仍未驗證其動態抓取成功率、請求安全邊界及記憶體開銷，因此本輪不直接接上瀏覽器。

未接入全網搜尋服務；沒有在未驗證品質與費用前新增付費 API。保留原有 21 個來源與每輪三場模型評估。下一個最值得處理的問題是提高「可信主辦規則 → 完整評估」的轉換，尤其可追溯的參賽資格、截止、AI 使用與出席義務；全網搜尋或動態抓取應用固定樣本驗證這個轉換，而非只看多抓幾筆。

- 版本已接收 100% 正式流量，健康檢查正常，仍為 21 個來源、每輪三場模型評估，Threads 自動私訊關閉。原有未提交變更未納入本輪提交。
- 以相同部署來源、真實外部網站與正式 Firestore 操作狀態驗證：冷啟動稽核嘗試 22 頁、發出 23 次 HTTP、取得 88 筆網址線索；後續稽核嘗試 23 頁、命中三次快取、發出 20 次 HTTP，仍取得 88 筆。頁數不同，因此不能由此宣稱固定的延遲或請求節省比例。
- 神腦仍回應 429，每次實際 429 僅發出一次請求；依當次 Retry-After 與最低等待政策處理，不能把等待時間一律解讀為 12 小時。沒有持續重試直到成功，也未確認伺服器端限流根因。
- 稽核未呼叫模型、未更新候選資格判斷、未寄送主辦詢問。驗證涵蓋外部抓取、共用狀態、單元／整合測試與正式版本健康；尚未以新候選重跑整個「搜尋 → 模型 → 推薦」正式排程，因此未證明合格機會的產出率提升。
